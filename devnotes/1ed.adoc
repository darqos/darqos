== Notes on the First Edition

The purpose of this document is to gather notes on the use of the First
Edition Darq system. This will include basic bug reports, but more
importantly, larger issues identified during use. It will inform changes
to the roadmap and the overall design.

All notes should be dated. Revisions, fixes, etc, should not replace the
initial note, but be added to its description.

'''''

* It's helpful to use Sqlite for things like the History service where
  a relational data model and queries are a good match to the
  requirements. But by default, that means using the host filesystem

** _What is needed to have eg. Sqlite run over the Storage service?_

*** Ranged Read and Write (methods 6 and 7 are reserved), so a page write doesn't rewrite the whole blob.

*** Truncate, or a ranged Write that sets the length.

*** Blobs found by a name the caller chooses, or a directory blob mapping names to keys: SQLite opens its files (db, -wal, -journal) by name.

*** A durability guarantee: a Put is on disk once it's answered, so it can serve as SQLite's sync barrier.

*** Maybe an atomic multi-blob Put, so the VFS can offer  SQLITE_IOCAP_BATCH_ATOMIC and SQLite needs no journal.

*** Python's sqlite3 can't register a VFS: it needs C, or apsw.
